# 日期语义数据层（暂名 IcynDate）产品与技术方案 v0.1

> 一人公司第一个对外收费产品。目标不是营收，是**走完"公开 → 获客 → 收款 → 维护"整个闭环**，并把账号、计费、文档站这套基础设施一次搭好，供后续 TTS 前端库与终端舱复用。

---

## 0. 一句话定位

**给 AI Agent 和应用开发者的"日期上下文"服务：输入一个日期和地区，返回它意味着什么。**

不是日历 App，不是万年历，不是风水工具。它是"任何需要理解日期的程序前面的那一层"。

### 0.1 为什么是它先上

| 维度 | 日期数据层 | TTS 前端 | Agent 终端舱 |
|---|---|---|---|
| 运维成本 | 接近零（静态数据 + 无状态 API） | 中（CPU 服务，但有评测维护） | 高（长连接、多端、平台风险） |
| 上线所需时间 | 4–6 周 | 8–12 周 | 已成型但市场挤 |
| 竞争 | 有免费源，但无"东亚语义 + Agent 友好"的整合 | 大厂在做，但前端层是空白 | 官方 + 开源免费 |
| 对你的价值 | 练销售肌肉、搭基础设施 | 中期收入主力候选 | 作品与技术信誉 |

### 0.2 明确不做

- 不做面向终端用户的日历 UI（未来可作 demo，不作产品）
- 不做风水/运势/择日预测类断言（只保留"传统民俗说法"字段，标明来源与性质）
- 不做个人日程、提醒、同步（那是 Google/Apple 的地盘）
- 不做健康食谱、人文内容（内容不是数据）
- 第一版不做用户自定义节假日（企业排班场景，留给 Pro 档）

## 1. 目标用户与场景

### 1.1 三类买家

**A. 做 Agent / LLM 应用的开发者（首要）**
Agent 需要知道"今天是什么日子"：排期助手要避开节假日，客服机器人要在春节前调整话术，日报 Agent 要知道"历史上的今天"作为开场。他们要的是一个 MCP server 或一次函数调用，而不是自己去拼五个数据源。

**B. 中国出海开发者**
做面向欧美/东南亚的产品，需要目标市场节假日、工作日、时区 DST 规则，而且要中文文档。

**C. 海外开发者做中文/东亚市场**
需要农历、节气、中国/日本/韩国/越南节日，以及"这个日子有什么习俗"这类语义，自己做几乎必错。

### 1.2 典型调用

```
"下周三是中国的工作日吗？如果是调休上班日也要告诉我"
"给我 2027 年所有中国法定假日及调休安排"
"今天农历几号、什么节气、传统上有什么讲究"
"历史上的今天（1 月 27 日）发生过什么，中英文各三条"
"美国、德国、日本三地在 12 月 24 日–1 月 3 日之间哪些天是假日"
```

## 2. 范围与数据模型

### 2.1 核心实体

```
DateContext            一个 (date, region) 的完整语义
├── civil              公历基本信息：星期、ISO 周、年内第几天、闰年
├── workday            是否工作日 / 是否调休上班 / 是否调休放假 / 下一个工作日
├── holidays[]         该地区当天的节假日（法定 / 非法定纪念日 / 宗教 / 商业）
├── lunar              农历：年月日、干支、生肖、闰月、是否月首月末
├── solar_term         节气：当前节气、下一个节气及其精确时刻
├── traditional        传统民俗（黄历宜忌、节令习俗），标 source 与 nature
├── history[]          历史上的今天（可按语言、类别、重要度筛选）
├── astro              日出日落、月相（可选，按经纬度）
└── tz                 时区信息、当天是否有 DST 切换
```

### 2.2 字段设计原则

1. **每条数据带 `source` 与 `confidence`**。法定假日来自政府公告 → `official`；调休预测 → `predicted`；民俗宜忌 → `folklore`。Agent 需要知道哪些能当真。
2. **多语言是一等公民**。`name` 是一个 `{zh, en, ja, ...}` 对象，不是字符串。
3. **地区用层级码**：`CN`、`CN-GD`、`CN-HK`、`US-CA`。节假日在不同层级有差异（如香港 vs 内地，美国各州）。
4. **时间一律 ISO 8601 + 时区**，节气给到精确时刻（`2027-02-04T10:46:00+08:00`），而不只是日期。

### 2.3 示例响应（节选）

## 3. 数据源清单

每个数据源三个问题：**许可能否商用、更新频率、谁来维护**。这一层是产品的真正成本，也是护城河。

| 数据 | 来源 | 许可（发布前逐一核实） | 更新 | 策略 |
|---|---|---|---|---|
| 农历 / 干支 / 生肖 | 自算。天文算法（VSOP87 / ELP2000 简化版）或采用公开的寿星万年历类算法 | 算法公开；实现自写 | 无需更新 | 与 `lunar-javascript`、`sxtwl` 等成熟库交叉验证 1900–2100 全部日期 |
| 二十四节气精确时刻 | 天文算法（太阳黄经） | 自写 | 无需更新 | 与紫金山天文台历年公布数据对拍 |
| 中国法定假日与调休 | 国务院办公厅年度通知 | 政府公文，可用 | 每年 11–12 月 | 人工录入 + 自动校验；未公布年份标 `predicted` |
| 港澳台节假日 | 各地政府公报 | 可用 | 每年 | 同上 |
| 日本 / 韩国 / 越南 / 新加坡 | 各国政府公告 + 农历派生 | 可用 | 每年 | 农历派生部分自动，其余人工 |
| 欧美主要国家节假日 | 政府官网；辅以 `Nager.Date`（MIT）、python `holidays`（MIT） | MIT 可商用 | 每年 | 以开源库为基线，用官方源覆盖修正，记录差异 |
| 时区与 DST | IANA tzdb | 公共领域 | 随 tzdb 发布 | 直接依赖运行时库，不复制 |
| 历史上的今天 | Wikipedia（各语言）"On this day" / 日期条目；Wikidata | CC BY-SA 4.0（须署名与相同方式共享）；Wikidata CC0 | 季度快照 | 自动抓取 + 清洗 + 重要度打分；响应中带署名与链接 |
| 黄历宜忌 | 传统通书规则（建除十二神、二十八宿、彭祖百忌等） | 传统文献，公共领域；实现自写 | 无需更新 | 只作 `folklore` 呈现，不作任何断言性表述 |
| 节令习俗 | 自编 + 引用公开百科 | 自写内容自有；引用部分标明 | 低频 | 首版覆盖中国主要节日约 30 条 |
| 日出日落 / 月相 | 天文算法 | 自写 | 无需更新 | 与 NOAA / USNO 公布值对拍 |

### 3.1 关于维基百科的具体注意

- CC BY-SA 意味着：你分发的**条目文本**必须保留署名并允许下游以相同许可使用。做法：`history[]` 每条带 `license`、`url`、`attribution`，文档明确写出。
- 你自己的**结构化字段**（重要度、分类、翻译对齐）是你的作品，可以另定许可。
- 不要一次抓全量。先抓 366 个日期条目的"事件"章节，清洗成 `(year, text, links)`，再用规则 + 小模型打重要度。
- 中文与英文条目内容不同，不要机翻对齐，各自作为独立数据源，`lang` 字段区分。

### 3.2 关于"预测调休"

中国调休安排每年年底才公布。对未公布年份，可以按历史规律给出 `predicted` 结果，但**必须**在字段和文档里标明，并在公布后立即更新。这是 Agent 开发者最在意的一点：宁可说"不知道"，不能说错。

## 4. 产品形态

三种交付形态，同一份数据：

### 4.1 离线包（免费，获客入口）

- `npm i @icyn/date`、`pip install icyndate`
- 内置：农历、节气、干支、黄历、中国 + 港澳台 + 日韩越 + G7 节假日（近三年 + 未来一年）
- 无网络、零依赖、MIT 许可
- 作用：GitHub star、SEO、信任建立。**离线包永远免费**。

### 4.2 MCP Server（免费 + 付费源）

- `npx @icyn/date-mcp`，一条命令接入 Claude Desktop / Cursor / 任何支持 MCP 的客户端
- 工具集：
  - `date_context(date, region, lang, include[])`
  - `holidays(region, year | range)`
  - `workdays(region, start, end)` → 工作日列表 / 计数
  - `next_workday(region, from, n)`
  - `lunar(date)` / `solar_terms(year)`
  - `on_this_day(date, lang, limit, category)`
  - `convert(lunar → solar / solar → lunar)`
- 本地模式用离线包；联网模式走 API 拿更多地区与最新历史数据。

### 4.3 托管 API（收费）

REST，OpenAPI 文档，API Key 鉴权。

```
GET  /v1/context?date=2027-02-06&region=CN&lang=zh,en&include=workday,lunar,history
GET  /v1/holidays?region=CN&year=2027
GET  /v1/workdays?region=CN&from=2027-01-01&to=2027-03-31
GET  /v1/on-this-day?date=02-06&lang=zh&limit=5
GET  /v1/lunar?date=2027-02-06
GET  /v1/solar-terms?year=2027&tz=Asia/Shanghai
GET  /v1/regions                                  列出支持地区与数据新鲜度
POST /v1/batch                                    一次最多 100 个查询
```

响应统一带 `meta.data_version`、`meta.generated_at`，便于客户端缓存与审计。

### 4.4 数据文件（Pro 附赠）

`holidays-2027.json` / `.csv` / `.ics` 等可下载文件。很多客户只想要一份能进数据库的表。

## 5. 技术架构

**原则：静态预生成 + 无状态 API，能不跑服务就不跑服务。**

```
data-sources/           原始数据与抓取脚本（Wikipedia 快照、政府公告录入表）
        │
        ▼  build（CI 每周 / 手动触发）
dataset/                规范化 JSON，按 region/year/lang 分片，带 data_version
        │
        ├──► packages/core       纯算法：农历、节气、干支、黄历、天文（TS + Python 双实现，共享测试向量）
        ├──► packages/offline    离线包 = core + 内置数据分片
        ├──► packages/mcp        MCP server（封装 offline 或调用 API）
        └──► apps/api            API：Cloudflare Workers / Deno Deploy 之类边缘运行时
                                   数据从 KV / R2 读取，无数据库，无状态
                                   鉴权、计量、限流走中间件
```

### 5.1 为什么双语言实现

npm 与 pip 两个生态是两拨用户。核心算法用一份**测试向量**（`fixtures/lunar-1900-2100.json`、`solar-terms.json`）约束两份实现，任何一边改动都必须过同一组向量。这与终端项目里"录制 cast 作黄金数据"是同一种方法。

### 5.2 API 层选择

- 边缘运行时（Workers/Deno Deploy）：冷启动几乎为零，全球就近，免费额度足够前期
- 计量：每 key 每日计数写 KV/Durable Object，月末汇总到计费
- 不要上 Postgres。数据是静态的，配置是几张小表，全部可以放 KV

### 5.3 与 TTS / 终端共享的基础设施

这一次要把以下东西做成可复用的：

- 账号与 API Key 签发（一个后台，三个产品）
- 计费（Paddle / Lemon Squeezy 作 Merchant of Record，处理 VAT 与销售税）
- 文档站（一个域名，三个产品各一个 section）
- 状态页与用量面板
- 品牌与 GitHub 组织

## 9. 风险与应对

| 风险 | 概率 | 应对 |
|---|---|---|
| 免费替代品（`holidays` 库、Nager.Date）足够好 | 高 | 不在"有数据"上竞争；差异化在东亚语义、Agent 友好、多语言历史、预测标注、维护承诺 |
| 收入天花板低 | 高 | 接受。它的任务是闭环与基础设施，不是主营 |
| 维基百科许可处理不当 | 中 | 每条带署名与链接；结构化字段与原文分离；文档写清 |
| 政府数据更新遗漏 | 中 | 年度更新日历放进 CI 提醒；未公布年份一律 `predicted` |
| 民俗内容被解读为迷信/误导 | 中 | 只呈现不断言；字段 `nature: folklore`；文档声明；不做"预测"类端点 |
| 一人维护 30+ 地区疲劳 | 中 | 以开源库为基线自动化，人工只覆盖差异；地区扩展按付费需求驱动 |
| 被大厂/平台吞掉 | 低 | 这个品类对大厂太小；真被吞掉说明验证成功，转向 TTS |
